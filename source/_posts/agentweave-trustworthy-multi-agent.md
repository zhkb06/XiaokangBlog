最近在准备 2026 第五届「未来杯」创新大赛，赛题一是「Agent 编排创新应用」。我和指导老师徐宇丰做了一套平台，叫**织流 AgentWeave**，定位一句话就能说完：

> 别人让 Agent 能干更多事，我们让 Agent 干的事可被验收。

这篇文章不写宣传稿，主要记录「为什么做、怎么做、做到了什么程度、哪里还不行」。

<!-- more -->

## 从一句很不舒服的问题开始

市面上的 Agent 演示都很好看：七个角色互相传话，最后吐出一份漂亮的报告。但我每次看完都会冒出一个问题——

**这份报告里的数字，凭什么是对的？**

把这个问题拆开，就是四道工程鸿沟：

| 鸿沟 | 具体表现 |
| --- | --- |
| 流程硬编码 | 换个任务就要改代码，编排无法被非开发者复用 |
| 调度黑盒 | 为什么选这个 Agent？没人说得清，出错只能猜 |
| 结果不可验证 | 模型说「已完成」，但没人核对数字对不对 |
| 没有反馈闭环 | 失败就是重来，几次之后还是失败，毫无收敛 |

这四件事不解决，多智能体就永远停在「能演示」。

![七个 Agent 协作，交出一份报告](/images/projects/agentweave/cover.png)

## 平台做了什么

织流 AgentWeave 是围绕「验证」来设计的：编排、调度、执行、验证、自循环、报告，一条链走完。

技术上它很克制：后端纯 Python 标准库，前端原生 JS/SVG，零第三方运行时依赖，离线 Mock 模型就能完整跑通，方便评审和同学一键复现。

![六层架构：引擎不碰模型，模型不碰状态](/images/projects/agentweave/architecture.png)

### 编排：把流程写成契约，而不是写成代码

流程用 DAG 描述，存成 JSON：节点可以是 Agent、工具、验证、循环修复或者人工闸门，边是有向依赖。

好处是「编排」这件事从代码里搬了出来：改流程不用改引擎，流程本身还能进版本库、被 review、被复用。

### 调度：分数、理由、负载，一次决策三样都留下

调度不是「谁先空谁上」，而是打分：

```
score = 0.40 × 能力匹配
      + 0.30 × 空闲度
      + 0.20 × 优先级
      + 0.10 × 历史成功率
```

五套策略可选：FIFO、轮转、能力匹配、负载感知、自适应。每次决策都会把分数、理由、当时的负载写进事件流，事后可以复盘「为什么是它」。

还有一个容易忽略的细节：策略是按单次运行隔离的（`Scheduler.fork`），两个并发运行不会互相串策略，但历史统计是共享的——这样自适应策略才是真的在积累经验，而不是每次都从 0.5 重新学。

### 验证：五层漏斗，13 个检查器

这是整个平台的核心。我们把它做成了从「格式对」到「统计上可信」的五层漏斗：

![五层验证漏斗](/images/projects/agentweave/verify-funnel.png)

- **L1 结构与非空**：字段齐全、JSON 可解析；
- **L2 数值对齐真值**：与隐藏真值比对，相对误差 ≤ 15% 才算过；
- **L3 代码重跑复现**：申报指标 vs 独立复算；
- **L4 跨 Agent 独立复算**：验证者自己重算一遍再比对；
- **L5 统计与评审**：样本量、R² 阈值、多重共线性、显著性、不确定度，必要时再上 LLM 评审。

判定规则只有一句：`passed = 置信度 ≥ 阈值 且 无硬性失败`。不给「平均分掩盖致命错」留任何口子，跳过的检查项也不计入分母。

具体实现上是 13 个检查器，覆盖 schema、非空、真值比对、代码复算、跨 Agent 校验、统计检验、数据质量、留出稳定性、共线性、显著性、不确定度等。

### 自循环：失败不是「再来一次」，而是结构化定位

如果验证没过，系统不会简单重试，而是把失败整理成反馈：哪一项没过、期望多少、实际多少、偏差多少，再定向重跑，最多 3 轮。

![一次真实的失败修复：42.3% → 100%](/images/projects/agentweave/loop-fix.png)

上图的例子是真实跑出来的：第一轮置信度 42.3%，wind 偏差 34.4%，自循环一轮后第二轮 100% 通过。

## 效果到底怎么样

同一个 12 节点任务，用三种方式跑（数据在仓库 `data/benchmark.json`，一条命令可复现）：

| 指标 | A 单 Agent | B 多 Agent 并行 | C 并行 + 验证自循环 |
| --- | --- | --- | --- |
| 耗时（s） | 0.16 | 0.39 | 1.03 |
| Token | 5,845 | 21,309 | 27,191 |
| 系数误差 | 34.4% | 34.4% | **7.1%** |
| 验证通过率 | 0% | 0% | **100%** |
| 置信度 | 87.3% | 89.0% | 93.0% |

![并行换速度，验证换确定性](/images/projects/agentweave/benchmark.png)

> **口径说明**
> 这组数据是**离线 Mock 模型**跑的（固定种子），用来验证机制是否成立，不代表真实大模型环境下的表现。真实模型链路已经支持 OpenAI 兼容接口，但我还没有用真 Key 端到端跑完整套评测，这一点后面会补。

结论不吹：并行换速度，验证换确定性。多花 66% 的 Token，换来误差降 80%、通过率从 0 到 100%，这笔账在我们关注的科研与工程分析场景里是划算的。

## 踩过的坑（这部分最真实）

做完之后我花了一整天做「不像演示」的排查，抓到的问题比想象中多：

1. **并发准入竞态**：并发上限设的 4，突发 8 个请求时放进来 5 个——因为「检查并发数」和「创建运行」不是原子的。加了准入锁之后复测 4/4 通过。
2. **SSE 回放永不关闭**：运行结束后再连事件流，连接会一直挂着。根因是回放循环里 `finished = data["finished"]` 被后面的日志事件覆盖回 `False`。
3. **产物下载 100% 404**：产物落在 `data/runs/<id>/`，而接口按 `<仓库>/runs/<id>` 找，路径兜底没覆盖到真实目录。
4. **取消接口 500**：代码里引用了一个不存在的事件常量，取消其实生效了，但接口报错。
5. **自适应策略其实没生效**：`record_outcome` 全仓只有测试在调，运行时的历史成功率永远是 0.5，权重根本没在自适应。
6. **未收敛没有硬上限兜底**：早期记录里有一批「循环未收敛」的失败运行，只能靠人工重跑。

这些问题最后都补了回归用例，测试从 174 个增加到 206 个，另外还修了 `.env` 不被加载、显式未知工作流会静默回退到场景等小问题。

## 还没做到的部分

说实话，这套东西离「产品」还有距离：

- **真实模型没端到端验证**：默认 provider 是 mock，真 Key 跑通的只有单点链路；
- **数据是合成的**：10 个行业场景的数据集都是生成的，没有真实客户数据；
- **性能没压测**：没做过高并发、长稳、故障注入；
- **产品化缺失**：单进程 + JSON 文件持久化，没有租户隔离、计量和 SLA。

所以对外我只说：这是一个**可离线复现的多智能体编排 + 可信验证框架**，不是可以直接交付的生产系统。

## 仓库与复现

- 代码仓库：[github.com/zhkb06/agentweave](https://github.com/zhkb06/agentweave)
- 仓库 `docs/` 下有方案书、项目白皮书、演示 PPT 和 3 分 42 秒的演示视频
- 复现（纯标准库，Python 3.11+）：

```bash
py -3.14 server.py --open-browser      # 打开 Web 控制台
py -3.14 scripts/run_demo.py --json    # 跑一次完整闭环
py -3.14 scripts/run_scenario.py --all # 10 个行业场景回归
py -3.14 -m unittest discover -s tests -t .   # 206 个用例
```

## 下一步

短期就三件事：接真实模型把整条链路跑通并留评测数据、找一个真实场景的数据做一次端到端、补并发与长稳压测。

长期想做的，是让「可验证」变成一种默认习惯——就像现在写代码会写测试一样，以后让 Agent 干活，也应该默认要求它交出一份能被复算的结论。
